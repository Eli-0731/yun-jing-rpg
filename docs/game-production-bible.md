## 第一部　我們要做什麼遊戲

### 1. 一句話

**在一個精巧得值得細看的仙俠大世界裡，「自己」從凡人開始，摸索出修仙是什麼感覺。**

### 2. 核心體驗

| 體驗 | 意思 | 怎麼做到 |
|---|---|---|
| **修仙的感覺** | 不是打怪升級，而是採藥、煉丹、練氣、打木樁、追靈獸、悟功法，慢慢從凡人變成修士 | 生活型修行活動，每一項都有手感和回饋；在家裡、洞府裡也能一直練氣 |
| **自己摸索** | 世界不告訴你答案；玩家靠觀察、好奇心找到東西 | 沒有強制任務，提示藏在環境裡；機緣藏在細節中（見第 4 節） |
| **精巧的世界** | 每座建築、每個角落都值得靠近看 | 建築模組化但細節密度高；近看有雕花、刻字、使用痕跡；可以進屋、爬上、鑽進去 |
| **這個角色就是我** | 玩家操控的就是自己 | 先做女主角試玩；長期做「上傳照片客製化角色」（見第 9 節） |
| **公平** | 不能花錢變強 | 出生資質由服務端一次決定、不能重抽；付費**只賣時裝**；所有資產由服務端判定 |

### 3. 遊戲結構

```text
創角（出生資質由服務端決定，不能重抽）
  ↓
新手大世界：前十個現實日（離線也計時），自由探索
  ├─ A 青溪河谷（出生地、新手村）
  ├─ D 古林（靈獸、古樹、進階採集）
  ├─ B 垂直山城（第十日測資廣場）
  ├─ C 裂靈湖（靈脈、秘境入口）
  └─ 散落在各區的「機緣」
  ↓
第十日：資質揭曉 → 選擇宗門
  ↓
宗門篇章（之後）：七宗方向、拜師、宗門專屬玩法、洞府、每週秘境、更大的州域
```

新手大世界不是教學關卡，而是一個**完整、可以一直回來探索的大世界**。宗門之後的新玩法另外規劃，不在這份總綱的近期範圍內。

### 4. 機緣系統（大世界探索的核心）

機緣是「只有認真探索的人才找得到」的東西，會影響角色之後的路。

| 類型 | 例子 | 怎麼發現 |
|---|---|---|
| 隱藏地點 | 瀑布後的洞穴、古樹根下的石室、屋頂上的暗格 | 看得到但要繞路、攀爬、或在特定時間才進得去 |
| 刻文與殘卷 | 石壁刻字、廢墟殘碑、書架上的舊冊 | 靠近閱讀；幾段合起來才看得懂 |
| 天時地利 | 只在清晨開的靈花、雨後出現的靈泉、月夜才現身的靈獸 | 依現實時間或遊戲天氣出現 |
| 人物連鎖 | 藥農的遺願、客棧主人的舊事、路邊老者的考驗 | 多次拜訪、帶對東西、做出選擇 |
| 環境謎題 | 調整水渠讓溪水改道、點亮廢墟燈陣 | 觀察周遭、試錯，可以重來 |

**規則：**

1. 機緣的獎勵由**服務端判定並記錄**，每個角色只能領一次；客戶端只負責顯示與演出。
2. 獎勵不能讓人「直接變強很多」。以功法領悟、稀有材料、外觀小物、與 NPC 的關係為主，維持公平。
3. **密度目標**：在新手大世界裡，玩家平均每走 30–60 秒就該遇到一個值得停下來看的東西（地標、互動物件、線索或機緣）；每個區域至少 10–20 個機緣，其中約三分之一真的藏得很深。
4. 機緣用資料描述（位置、觸發條件、需要的線索、獎勵代碼），場景生成器依資料擺放；企劃、美術和程式各自改自己的部分，不互相卡住。

## 第二部　世界與美術

### 6. 品質標竿

- 目標是五張世界方向圖的完成度，並以原神璃月的精細程度當**最低標**，希望做得更好。
- 但要誠實：璃月是上百人的團隊做出來的。我們要贏的不是「面積」，而是**密度與用心**：每一小塊都手工調過，每個角落都有東西，並靠程式化工具（地形、散布、模組）把人力花在最該花的地方。
- **做法：一小塊做到滿分，再複製方法，而不是一大片都做到六十分。**

### 7. 世界怎麼構成

| 層 | 用什麼做 | 誰負責 |
|---|---|---|
| 地形 | Unity Terrain，由資料（高度點、平台、道路）產生；斷崖、石峰用模型 | 核心組 |
| 水 | 地形挖渠＋水面材質；瀑布用模型加粒子 | 核心組 |
| 道路 | 泥土＋碎石畫在地形上；路緣、石砌護岸、石階、橋用模型 | 核心組（地形）、協作者（模組） |
| 建築 | 模組化建築套件（牆、柱、瓦、窗、門、欄杆），組成房屋、宗門、廟 | 協作者做套件，核心組組裝 |
| 細節 | 雕花、匾額、燈籠、器物、刻字、使用痕跡；可互動的小物件 | 協作者 |
| 植被 | 樹、竹、花草；依遮罩自動散布；古樹地標 | 核心組（散布規則）、協作者（模型） |
| 氣氛 | 霧、雲海、光線、天空、一天的時間、天氣 | 核心組 |
| 室內 | 獨立場景，從門口淡入淡出進入 | 協作者做室內套件，核心組組裝 |

### 8. 「精巧建築」的做法

1. **建築語言統一**：青瓦、木構、石基、少量氧化銅。每種構件（柱、樑、斗拱、窗格、欄杆、瓦當）都做成模組，並準備多種變體。
2. **三層細節**：
   - 遠看：輪廓清楚（屋頂曲線、層次）；
   - 中景：看得出結構（柱、窗、欄杆）；
   - 近看：有雕花、刻字、苔痕、裂縫、器物。
   三層各自有 LOD，手機也跑得動。
3. **可以進入、可以攀爬**：重要建築能進屋；屋頂、塔樓、橋上、城牆可以走上去。高處要放東西，獎勵願意爬上去的玩家。
4. **每棟都有故事**：誰住在這裡、做什麼的，並用擺設表現出來（藥舖有藥櫃，鐵匠有砧板）。機緣常藏在這些故事裡。

### 9. 角色

| 階段 | 內容 |
|---|---|
| 現在 | 女主角 Heroine-01：z1nnz 在外部生成，再到 Blender 拼接（見說明文件）。先讓我們能試玩 |
| 下一步 | 統一的身體標準：一套骨架、一個基礎身形，衣服分部位（上衣、下身、外袍、鞋、髮型、飾品）。**時裝都做在這套標準上**，換裝才不會穿模 |
| 長期 | **上傳照片客製化角色**（研發項目，見下） |

**上傳照片客製化角色（長期研發）**

- 技術路線：用照片產生臉部特徵，再套到我們的基礎頭部上（調整形狀參數、膚色、髮型），而不是讓每個人有一套完全不同的模型。這樣時裝、動作、效能才能共用。
- **隱私**：照片是個人生物特徵資料。必須取得明確同意、說清楚用途、盡量在裝置上處理或處理後立即刪除、讓玩家可以刪除。上線前要另外做法律與隱私審查。
- 先做「捏臉系統」（滑桿調整），照片功能之後再接上去。

### 10. 付費（只賣外觀）

- 只賣時裝、髮型、飾品、坐騎外觀、洞府裝飾之類**不影響強度**的東西。
- 不賣修為、資質、材料、靈石、機緣。
- 時裝都依第 9 節的身體標準製作；付費、退款與帳本由服務端處理。

## 第三部　程式怎麼寫

### 11. 整體架構

```text
┌────────────── 客戶端（Unity 6000.0.82f1，URP，Input System）──────────────┐
│ 場景：各區域一個場景＋室內場景；由資料驅動的生成器產生                    │
│ 規則：純 C#（不依賴 MonoBehaviour），可單獨測試，與原型 JS 逐項對照       │
│ 表現：MonoBehaviour 只負責顯示、輸入、動畫、音效                          │
│ 平台：Windows、瀏覽器（WebGL／PWA）、Android                              │
└───────────────────────────────▲──────────────────────────────────────────┘
                                │ HTTPS（requestId、票證）
┌───────────────────────────────┴──────── 服務端（NestJS）──────────────────┐
│ 角色與出生資質、十日計時、背包、帳本、機緣領取紀錄、修為、宗門、時裝商店  │
│ 所有資產與獎勵在這裡判定；重送不重複發放；斷線與重啟不重複扣料            │
└──────────────────────────────────────────────────────────────────────────┘
        多人（之後）：FishNet 區域伺服器，只同步位置與表演，不決定資產
```

### 12. 寫程式的規則

1. **規則和畫面分開**：遊戲規則（遭遇、煉製、練功、機緣條件）寫成純 C# 類別，可以在沒有畫面的情況下測試。協作者用 JS 做原型時，移植後要用錄下的劇本逐項對照（新手村已這樣做：A 的遭遇、Johnny 的木樁）。
2. **內容用資料描述**：地形、道路、擺件、採集點、機緣、NPC 對話都放在 JSON（之後可改為 ScriptableObject）。程式只讀資料，不寫死座標。
3. **場景由生成器產生**：場景檔不手改，也不進 Git；改資料或生成器，再重新生成。這樣可以重建、可以審查、不會互相覆蓋。
4. **互動統一介面**：目前的互動（F 鍵站點）是一串 if 判斷，之後重構成「可互動物件」介面加登記表，新增互動不用改核心程式。
5. **輸入一律走 Input System**：鍵盤、滑鼠、觸控、手把都要能操作；觸控是一等公民，不是之後再補。
6. **文字一律用打包字型**：Noto Sans TC 與 Noto Serif TC；不依賴作業系統字型。
7. **客戶端不能決定資產**：客戶端送「我做了什麼」，服務端回「你得到什麼」。

### 14. 測試與驗收

| 層級 | 工具 | 什麼時候跑 |
|---|---|---|

**今天學到的教訓**：兩個大錯誤（地形沒有碰撞、鍵盤滑鼠沒有作用）都通過了舊的 smoke，因為 smoke 繞過了玩家實際的操作方式。之後每個 smoke 都要**走玩家真的會走的路**。

## 第四部　模型怎麼建

### 16. 建模流程（每一件新模型都照這個順序）

1. **三視圖**：用本機 Codex CLI 的生圖產生正、側、背三視圖，檢視後存到 `art/references/<asset>/`，並附提示詞。
2. **量尺與拆件**：在 1.75 m 人形尺旁定尺寸、原點、接口（照[接地規格](execution/2026-10-29/14-grounding-spec.md)）。
3. **腳本建模**：Blender 5.2，寫成 `tools/art/build_*.py`，可以重建。
4. **細節**：先確定輪廓，再加細節；近景細節服務玩法辨識。
5. **UV、材質、貼圖**：材質數盡量少，共用貼圖集或可平鋪材質。
6. **LOD 與碰撞**：至少兩層 LOD；碰撞用簡單形狀，寫進 `model_info.json`。
7. **QA**：blender-asset-qa（game profile），錯誤全部修好。
8. **匯出與回匯**：GLB 與 FBX，重新匯入比對尺寸、面數、材質。
9. **進場景**：寫進擺件資料，生成場景，跑接地驗收，拍玩家視角截圖。
10. **README**：來源、作者、做了什麼、**還沒驗證什麼**。

### 17. 模型分類

| 類別 | 例子 | 原則 |
|---|---|---|
| 擺放件 | 道具、器物、NPC | 原點在底部中心，不附地面底板 |
| 結構件 | 橋、石階、平台、建築模組 | 接口表；地形去接它 |
| 散布件 | 單叢草、花、石 | 由規則自動擺放，要輕量 |
| 地標 | 古樹、宗門、測資廣場 | 高細節＋多層 LOD，是畫面焦點 |
| 角色與時裝 | 女主角、NPC、時裝 | 統一身體標準與骨架 |

### 18. 用 AI 的方式

- AI 三視圖是**設計參考**，不是工程圖；三面矛盾就重新生成，或標明「推定設計」。
- AI 產生的 3D 模型（外部網站、Blender 的 generate_3d）只當**起點**，一定要整理拓撲、UV、比例與面數，並記錄來源與授權。
- 使用者提供的外部素材，如果授權不允許散佈，就只留在本機。

### 22. 完成的定義

一件事要四個狀態都說清楚才算完成：**進了 Git／在場景看得到／玩家能互動／服務端有保存**。截圖或本機演練，不能說成「玩法已完成」。

## 第六部　風險與要先決定的事

| 風險或決定 | 說明 | 建議 |
|---|---|---|
| 範圍太大 | 五區大世界加上精巧建築，工作量非常大 | 嚴格照 P0–P6 走；每區先做一小塊到滿分 |
| 瀏覽器版的極限 | WebGL 下載大、手機效能有限；目前 105 MB | 瀏覽器版當試玩與快速分享；正式手機版用 Android／iOS 原生建置；瀏覽器版分區下載 |
| 照片做角色 | 隱私、法規、技術都難 | 先做捏臉；照片功能列為研發，上線前做法律審查 |
| 付費 | 不能破壞公平 | 只賣外觀，寫進服務端規則 |
| AI 素材授權 | 外部生成或下載的素材授權不一 | 每件記錄來源與授權；不明的不進 Git |
| 協作者署名 | GitHub 上看到 Claude 署名，是協作者自己的 Claude Code 預設行為 | 請協作者關閉 Co-Authored-By；核心組一律用 z1nnz |

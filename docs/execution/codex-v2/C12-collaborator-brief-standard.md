## 1. 一句話任務

依照我們現在的**工作流程、開發方向、開發架構與先後順序**，安排協作者該做什麼、什麼時候做，並寫出 A、B、C 的下一批工作包。

重點不是「新理念」本身，而是**順序**：
- 現在這個階段需要什麼；
- 什麼要先做好，別的東西才做得下去；
- 協作者的工作怎麼和 Claude Code、Codex 的工作接起來。

## 2. 為什麼要做

- z1nnz：「按照我們現在的工作流程、工作規劃、整體開發方向和開發架構，先做什麼、後做什麼，去安排協作者的工作包。」
- 過去的工作包常常只說「做什麼」，沒說「放在哪、為什麼現在做、做完接給誰」。結果有的東西做好了卻沒地方放，有的要等別人先做完才用得上。
- 工作包必須排在開發順序裡：每一份都服務**目前這個階段**，而且前置條件都已經滿足。

### 每一件東西的流程（不能跳步）

```text
① 位置（格位，Claude Code 定）
  → ② 三視圖（z1nnz 看過）
  → ③ 灰模放進遊戲看比例（Claude Code 看）
  → ④ 成品
  → ⑤ PR 審查（pr-review.md）
  → ⑥ Claude Code 接進遊戲，加伺服器動作與自動測試
```

- 工作包只能從前置條件已經滿足的那一步開始。沒有格位的東西，先請 Claude Code 定格位，再發工作包。
- 角色（包含 NPC）由 z1nnz 親自製作，不排給協作者。

### 一次給多少

- **每位協作者同時只開一個 PR**。上一個審完合併，才開下一個，免得 Claude Code 審不完、接不完。
- **一批的分量**約 14 或 42 小時（過去用過的批次），分兩段交：第一段要能單獨驗收。
- **Claude Code 的接入量也要算進去**：每一批交件，Claude Code 要花時間接進遊戲、寫伺服器動作、加測試。三個人同時交大批，整合會塞車。工作包裡寫明預計的交件日期，三人錯開。

## 5. 寫工作包的規則

1. **位置先於模型**：沒有格位就不發工作包。需要新格位的，寫在 `questions-for-claude.md`，由 Claude Code 加進區塊規劃。
2. **一份工作包只有一個主題、一個區塊**，不要一份包山包海。
3. **分量要和協作者過去的實際產出相當**：
   - 參考：A 的 #45 一輪約 24 個形體與一個可玩展示；
   - 不要少到半天做完，也不要多到兩週做不完；
   - 寫出總時數（過去常用 14 小時或 42 小時的批次）。
4. **品質優先，不寫面數上限**：每件寫面數參考值和「要附 LOD1／LOD2」。不能要求協作者為了數字減面（z1nnz 2026-10-30）。
5. **重複件寫數量**：例如「這段河 100 m，大約放 14 段」，讓協作者知道 LOD 很重要。
6. **玩法一定寫到伺服器**：只做展示的部分要明說「這是展示，不算進遊戲」。
7. **不交代**：工作包裡可以寫真相（給協作者理解），但要標明「這段給你理解，不能出現在遊戲文字裡」。
8. **用語照用語表**；不用「洞府」「背包」。
9. **協作者之間的接口寫清楚**：水接口、材質名、尺寸，誰先定、誰跟著用。

## 所有人共同交付規則

1. 從最新 `main` 開自己命名的分支，在自己目錄作業；開始前看 `AGENTS.md`、`docs/approved-plan.md`、`docs/status.md`、`docs/work-ownership.md`。昨日 PR 尚未合併時，需在自己的 README 寫明所依版本與如何切換；不要把昨日未合併分支整包複製進新 PR。
2. **每件自行製作的模型先以 AI 生成正、側、背三視圖，檢視輪廓與比例並保存到各自 `art/references/...`，才開 Blender 建模。** 參考圖、母稿、GLB、至少一張近景及一張場景尺度圖一併交付。相似小物可共用一張清楚標號的多物件三視圖板，但每件仍須有可辨識的三個方向。
3. 風格為古風修仙的青溪生活感：暖灰石、舊木、青銅小件、草木綠與清澈青溪水。避免直接複製他人遊戲的造型、UI 或技能圖示；不把來源未登記的外來模型收入 PR。
4. 提供真實尺寸、碰撞建議、近景與遠景版本或合理 LOD 規劃。模型不穿插、不漂浮，材質及貼圖路徑可在新檢出下正常載入。因手機優先，先控制透明葉片、材質數和實例數。
5. 玩法以獨立入口可操作，不只交設計文字或靜態圖；資料規則與 UI 分開。可用 PWA 展示，但所得、消耗、獎勵都標為本機展示，不宣稱正式入帳。若將來涉及正式物品變動，提供服務端請求／收據契約，避免前端自報獎勵。
6. 分兩批 PR 或一個 PR 的兩次清楚提交：第一批約 14 小時交一半模型和可玩的最小循環；第二批約 14 小時補滿模型、玩法分支、README、檢查及交接畫面。未完成項寫在 PR，不以佔位檔充數。
7. 作者署名、原始參考、測試命令／結果及已知缺口寫在各自 README。z1nnz／Codex 負責最後主場景接線，協作者不要自行改動主場景來展示。

## 接手順序

先看三個獨立展示及模型近景，確認輪廓、尺寸和玩法，再由核心組把 A 的遭遇區、B 的丹房、C 的回村互動依空間順序接到同一個青溪入口。整合後再測 Unity 編譯、操作、資產收據與手機負載；目前尚不能宣稱三段已在 Unity 同場可玩。
